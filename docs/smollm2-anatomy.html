SmolLM2-135M Anatomy

A model written from scratch in PyTorch, loaded with the published weights, continuing a prompt. This page shows what was built, what the downloaded files contain, and how one prompt becomes text, using real numbers from the run.

1 · Build

We built the circuit; the weights were downloaded

An LLM has two parts: the structure (a blueprint of which numbers get multiplied and added, in what order) and the weights (the 134.5 million constants fed into that circuit). The structure is hand-written in model.py. The weights were trained by Hugging Face on about 2 trillion tokens. No training happens here.

Weight names map one-to-one onto our module names, so loading them only requires stripping the leading model. prefix.

If a single part of the circuit were wrong, the output would be gibberish. Compared with the reference implementation in transformers:

2 · Files

The downloaded files

They are cached under ~/.cache/huggingface/hub/models--HuggingFaceTB--SmolLM2-135M/. Of the 272 MB total, 98.8% is the weight file model.safetensors.

Inside a safetensors file

The format is simple: a header length, a JSON header that works as a table of contents, then raw numbers. It cannot contain executable code (hence "safe"), and the offsets in the header let a loader read any tensor directly.

// The actual JSON header (first two entries)
"model.embed_tokens.weight": {"dtype": "BF16", "shape": [49152, 576], "data_offsets": [0, 56623104]},
"model.layers.0.input_layernorm.weight": {"dtype": "BF16", "shape": [576], "data_offsets": [56623104, 56624256]}

BF16 (bfloat16) is a 2-byte float. 134,515,008 values × 2 bytes ≈ 269 MB, which matches the file size. We convert to float32 (4 bytes) on load, so the model takes about 540 MB in memory.

Where the 134.5 million parameters go

tokenizer.json (BPE)

49,152 vocabulary entries and 48,900 merge rules. Starting from single bytes, frequent pairs are merged step by step (for example Ġ + t → Ġt) to build word pieces. Ġ marks a preceding space.

From prompt to text

Ten tokens. The model receives only these integers and never sees characters. Repeated pieces (Ġa, ,) get the same ID.

Ġ is a space. The tokenizer first turns text into bytes, then maps each of the 256 byte values to a printable character. Invisible bytes such as space (0x20) are shifted by 256, so 0x20 + 0x100 = U+0120, which is Ġ. The space attaches to the following word, so "upon" at the start of a sentence and in the middle of one are different tokens.

Folding the space into the word roughly halves the token count, and nothing is lost: decoding reproduces the original text exactly.

2IDs to vectors (embedding)

Each ID selects a row of the embedding table (49,152 rows × 576 columns), giving 576 numbers per token and a 10×576 matrix overall. Training has left something like "village-ness" encoded in the numbers of the "village" row.

3Through 30 decoder layers

The 10×576 matrix passes through the 30 layers in order. A layer does not replace the vectors; it adds the results of two computations to them (residual connections).

RoPE encodes position as a rotation angle applied to the vectors (θ = 100,000), which lets attention tell which position each token is at.

4Vector to next-token probabilities

The 576-dim vector at the last position (,) is dotted with the embeddings of all 49,152 tokens (lm_head), and softmax turns the scores into probabilities. The actual top five:

5Roll the dice (sampling)

--temperature 0.8 sharpens the distribution a little, --top-k 50 drops everything outside the top 50, and one token is drawn by probability. This run drew ' there' at 24%. A different --seed can draw ' lived' and a different story. With --temperature 0 the top token always wins and the output is deterministic; verify.py uses this greedy mode.

6Append and repeat (KV cache)

The chosen token is appended and steps 1–5 run again. Re-running every token through 30 layers each time would be wasteful, so each layer keeps the K and V it computed, and later steps process only the new token.

7IDs back to text

The tokenizer turns the ID sequence back into a string for printing. Characters such as Japanese span several tokens and would come out garbled if cut mid-way, so the script decodes the whole sequence each time and prints only the new part.

4 · Takeaways

What this shows

  • The model only predicts the next token. Plot and coherence are side effects of repeating that. In this run, Oliver the owl ends up addressing "the wise old owl" as "Oliver", an inconsistency that reflects the limits of 135M parameters.
  • This is a base model. It is not SmolLM2-135M-Instruct, which is further trained to follow instructions, so it continues text instead of answering questions.
  • Non-English text is expensive. The training data is mostly English, so the vocabulary has almost no Japanese. The five characters of こんにちは ("hello") become nine UTF-8 byte fragments:
